# Privacy: data inventory, processors and rights

Basis for the record of processing activities (ISO/IEC 27701 7.2.8; SOC 2 P1–P8). **Alma has no servers of its own, with one opt-in exception: the relay for remote access (spec 027), described in section 2 and off by default**. Everything Alma stores lives on the computer of the person who uses it (`%APPDATA%\Alma` and the folders that person chooses). Whoever installs it is the controller; the providers in section 2 are processors or sub-processors depending on what the person configures.

### Chat attachments (spec 030): the notice, the measures and their limits

What is built, from the code. The desktop composer and, since spec 031, the paired phone's chat (next subsection); Telegram, WhatsApp, voice and company agents' conversations take no attachments. The phone never receives the files themselves, only their names, kinds and sizes.

- **What leaves the machine.** Attaching sends nothing. When the person sends the message, the model sees only a reference line per attachment (id, name, size; for a picture also its path) under a heading that says it is data and not instructions. A document's text reaches the provider only if the agent calls `read_attachment`, and then it is the answering provider that receives it as a tool result. A picture reaches the vision model's provider only if the agent calls `look_at_image` on it. The file name travels on the reference line.
- **The notice.** On the first send with attachments the composer shows which provider(s) will read the attached content, for the thread's provider and, when a picture is attached, the provider the looks would use (see the next bullet). Accepting it is remembered per provider in settings (`attachments.noticeAcknowledged`) and only a provider not yet accepted shows it again; cancelling keeps the text and the chips. It informs; it does not stop anything afterwards, and it is checked in the window, not by the coordinator. It does not cover the providers of sub-agents started with `delegate_task`, nor a model the person switches to after accepting.
- **Which provider looks at the pictures (spec 038), and when a provider chosen alone is used.** The vision provider is chosen in «Configuración → Imágenes» (before spec 038, in «Configuración → Casa»). One function in `shared` (`resolveVision`) decides it from settings alone, and both the notice and the looks (`look_at_image`, `camera_look`, camera watches, plan-from-photo, a picture attached in the chat) call it, so the provider the notice names is the one that receives the picture; it is decided with no network call, so a failed model listing never changes it. The rule (the acknowledgement gate): a provider with a **typed model** is used as it is; a provider with **no model** is used only if it is in `attachments.noticeAcknowledged`; otherwise (nothing chosen, or a provider chosen alone that was never confirmed) the looks go to the model of the house agent, else the default agent, else any agent with a key, else the first agent, as they did before. The gate is read at every look, so a camera watch, which has no notice of its own, never sends a still to a provider the person only clicked or inherited, and starts using the provider on its next check once it is confirmed. Picking a provider in «Imágenes» that is not yet in the list opens a confirmation that names it and says that the pictures attached in the chat, camera stills and plan photos will be sent to it; «Confirmar» saves the provider, an empty model and the acknowledgement in one update, «Cancelar» changes nothing. When a provider has no capability rule (DeepSeek, Vercel) the confirmation also requires a model. A provider chosen alone, with a key and with a rule, is completed by listing its models with the person's key (the key goes to that provider, as for any call) and taking the last id in numeric-aware name order that its rule accepts; a failure to list or find one is an error to the person and the picture goes nowhere else.
  - **Residual: a pair carried over from Casa.** A provider and a model saved under Casa before spec 038 are copied once to «Imágenes» and, being a typed pair, keep working exactly as they did, without ever having been acknowledged: camera stills and plan photos keep going to that provider with no notice. Only a provider carried over **without** a model is held back until confirmed (the card says so in one line and offers a button). More generally, **a pair typed or carried over is used without an acknowledgement** (a typed model is a deliberate choice of provider and model, spec 038 BR-2); the Images tab itself does not create one for a provider not yet confirmed, because the model field's Save goes through the same confirmation as picking the provider, but a pair from a hand-edited settings file is used as it is.
  - **Residual: one list.** The acknowledgement is a single list shared by the chat notice, the phone's confirmation and this dialog. Accepting a provider in the chat notice (for example because a conversation's agent uses it) also counts as confirming it for seeing, so a provider chosen alone later is used without asking again. A typed model is used whatever the list holds, and the «Automático» chain has no gate: the agent's own provider receives the pictures, as before, and the notice names it.
  - **Residual: capability is by id, not verified.** DeepSeek and Vercel AI Gateway are marked as having no known seeing model (decided on the owner's delegation, open to veto, because their cards say «solo texto» and their ids mix labs), so nothing is picked for them automatically; a model typed by hand is sent pictures with no check that it can see them. For Anthropic (`claude-*`), xAI (`grok-*` chat ids; an id containing `vision` is never auto-picked) and Meta (`muse-spark*`) the rule is a pattern on the id. «The newest» is the last id in alphabetical, numeric-aware order, not the latest release: across families it is an order of names (for Anthropic it lands on the family whose name sorts last), so the pick can be a model the person would not have chosen, and it can change when a provider lists a new id. The pick is cached for the life of the process.
  - **Not verified.** No real provider was called with this code: that the listings of Anthropic, xAI and Meta return the ids the rules expect, and that the model picked really sees, is unobserved. The confirmation dialog and the cards were not rendered or clicked in a real window; the dialog's portal and its capture of Escape are reasoned from the code.
- **Secret-looking names.** A file whose name (or path, when the page knows it) matches `.env*`, `.npmrc`, `.netrc`, `*.pem`, `*.key`, `*.pfx`, `*.ppk`, `id_rsa*`, `id_ed25519*`, `*.kdbx`, `passwords.*`, `credentials*`, `Login Data` or `Cookies` asks for a confirmation before it is attached. It is a warning, not a refusal, and it looks at the name only, never at the content.
- **Masking.** Text the agent reads from an attachment has values that look like secrets replaced by `[masked]` before it reaches the model (the patterns of the audit trail's `redact()` plus private-key blocks, AWS access key ids, GitHub tokens, Google API keys and Slack tokens), and the tool result says how many were masked. This is pattern matching: a secret in a format the patterns do not know goes through, and a value in a quoted JSON key such as `"password": "x"` is not caught ([RISKS.md](RISKS.md) R‑16). Picture pixels are never scanned.
- **Picture metadata.** PNG, JPEG and WebP are stored without their EXIF, XMP, text and similar chunks (location, camera, author, orientation). The pixels are copied byte for byte and the original file is never touched. A GIF is stored as it is. A picture that does not parse completely is refused, never stored with its metadata. The cut is a byte-level rewrite without an image decoder, and colour profiles are kept ([RISKS.md](RISKS.md) R‑16).
- **Retention.** The 30 days count from the last time the conversation was opened in the desktop window or got a message from the person; routine, house-rule and company runs do not count. The sweep runs at start and every 12 hours, skips a conversation with a run in progress and deletes only files this feature stored. Legacy inbox pictures, Telegram photos and camera stills keep their rule (until «Borrar mi historial»). Since spec 031 the first read of a conversation by id on the paired phone (not the held repeats, not «load earlier», not the list and not the Chat tab's state poll) also counts as opening it. The files of a conversation that no longer exists are erased by the next sweep, whatever their age ([RISKS.md](RISKS.md) R‑16).
- **Logs and the audit trail.** `attachment.store`, `refuse`, `remove`, `sweep` and `delete-failed` carry ids, kinds, sizes, reasons and counts, never a name or a content. `attachment.open` carries only the outcome.

### Files from the paired phone (spec 031): what is different

Built, from the code; nothing of it was run on a real phone (see the end of this subsection).

- **Gate.** A separate sub-switch under Chat, «Send files from the phone» (`remote.sendFiles`), off at every turn-on and turned on only through a native confirmation in `main`. The confirmation says the files are kept 30 days on the PC and read by the model provider of the agent that answers, and names the providers (the remote chat's agent and, because pictures go to the vision model, the vision provider). Allowing it records those providers as acknowledged, in the same list as the desktop notice; Cancel records nothing.
- **Where the notice is accepted.** Only on the PC (that dialog or the desktop composer's notice). The phone never acknowledges anything. A put is refused as `notice-needed` while a provider that would read the file is not acknowledged, and the check is made again when a message that carries the files is sent (the conversation's agent may have changed). It covers the conversation's provider and the provider the looks would use after the gate (spec 038, previous subsection); it does not cover the providers of sub-agents started with `delegate_task`.
- **In transit.** One file is one request, at most 700 000 bytes (the request cap does not change), over the tailnet or, with the relay selected, as a sealed frame the relay cannot open. Nothing else is contacted. The phone shrinks a big picture before sending as a convenience; the PC trusts none of it and re-checks type, content, size and name on the bytes it receives, strips location and camera metadata, and refuses a secret-looking name with no override.
- **On the PC.** The file is stored by the same store as a desktop attachment and waits as a *pending upload* until a send binds it, at most 5 per phone, 15 minutes each (list under the table above). A put restarts the target conversation's 30-day clock even if the file is never sent. Pending uploads are not purged when only History or «continue conversations» is turned off; they expire in 15 minutes.
- **Audit.** A put and a removal leave an entry with the device id, the outcome and, for a stored file, its kind and size; a send that carries files adds their count. Never a name, an id, a text or base64. A refused put records only that it was refused, not why.
- **On the phone.** Chips and bytes live in the page's memory and are dropped once uploaded; nothing is stored, every response is `no-store`, the service worker never handles `/api/`. Alma cannot stop the person from copying or screenshotting what the phone shows.
- **Not verified in practice.** The camera, gallery and files sheet, the canvas shrink of real camera photos, iOS handling of HEIC pictures, the PC dialog and the PC settings row were not run on a real phone or in a real window; the tests cover the pure rules, the channel over the test transport and the rendered markup only.

### Alma's relay for remote access (spec 027): who runs it and what it can see

This is the maintainer's statement of fact, not legal advice. It applies only to a person who chose «Alma's relay» for remote access (it is off by default, Tailscale is the default, and nothing below happens otherwise). **Status: built, not deployed.** No relay runs yet; this section describes what the code is built to do and what the maintainer must still verify on the real platform (marked *to verify*).

- **Who runs it.** The project maintainer, personally, on voluntary donations; there is no paid tier and no feature depends on a donation. It is hosted on Cloudflare (Workers and Durable Objects). Operator's jurisdiction: Argentina. Abuse contact: `abuse@almaproject.app` (an address that forwards to the maintainer). The monthly budget ceiling is USD 5. The publish check (`pnpm run relay:publish-check`) would block publishing if any of these were ever a placeholder again.
- **What the relay and its operator can never read.** The text of messages and answers, notes and their paths, images and camera stills, approvals, the path and query of any request, headers (including the session token), device ids and names, scopes, the pairing secret and code, step-up assertions, push subscriptions, and the session keys. All of it is sealed on the PC and on the phone with keys the relay never has (ECDH P-256, AES-256-GCM); the relay forwards the sealed frames and never opens one.
- **What the relay and Cloudflare can see, by construction.** The network address of the PC and of each phone, TLS metadata, when a PC or phone connects and disconnects, whether the PC is online, the routing id (it is the first part of the host name `<routing id>.<relay domain>`, so DNS and the TLS handshake of the phone's network show it too), and for each frame its direction, size, time, and the plain envelope of the frame (type, session id and counter). The routing id is random and says nothing about the person.
- **Traffic analysis.** Sizes and timing are visible and can hint at what kind of thing a frame is (for example a large frame after a camera request). There is no padding. This is a limit of any relay, stated here and in the wizard.
- **What the relay application keeps.** Nothing. Addresses, routing ids and counters live in memory for the life of a connection or a rate window and are gone after it; the code uses no storage of any kind (a source scan enforces it) and holds no routing-id binding across a restart. Its only log lines are aggregate counters (frames forwarded, registrations, refusals by reason) with no address, id or payload.
- **What Cloudflare keeps.** Outside the relay's code and under Cloudflare's own policy. Not yet verified (spike V9): which logs and analytics Cloudflare produces for Workers and Durable Objects and which can be turned off. Until the maintainer reads the account settings and writes the answer here, assume that Cloudflare, as the host and the TLS terminator, can record the address, host name (routing id), time, size and status of every request and the connection events of the PC's socket, and keeps them as long as its policy says. Cloudflare sees only the sealed frames and the public phone app files; it cannot read the content. The maintainer minimizes what the account records as far as the platform allows.
- **Certificates.** The relay uses a wildcard certificate so that per-PC names are not listed one by one in public certificate-transparency logs (*to verify* on the issued certificate, spike V8). This is different from Tailscale, where the machine name is public.
- **The phone app comes from the relay.** The first time (and on updates) the phone downloads the app from the relay. Whoever runs the relay, or controls its Cloudflare account, could deliver an altered app, and the browser cannot prevent a deliberate swap of the service worker; the PC signs the hash of the official app and the phone refuses one the PC did not announce, which catches a stale, wrong or partly altered deployment, not a deliberate one. The hash of each release is published so anyone can compare it. This is the honest limit of end-to-end encryption in a web app ([RISKS.md](RISKS.md) R-14 (n)).
- **Retention and exit.** Nothing is kept by the relay, so there is nothing to delete there. «Borrar mi historial» deletes the PC's relay credentials and routing id and disconnects the PC; «Exportar mis datos» shows the chosen connection, never a credential. If the relay ends (the monthly cost above USD 5 for 3 consecutive months, or the maintainer can no longer run it) there are 60 days of notice in the app, the docs and the release notes, a final release that reports the relay as ended and leaves Tailscale untouched, and the hosting account and any provider logs are deleted at the end. These contents are provisional until the maintainer confirms them.

## 3. People's rights and how they are handled

| Right | How |
|---|---|
| Access and portability | «Ajustes → General → Privacidad → Exportar mis datos»: copies the conversations, companies, audit trail, routines and the voiceprint into a new folder (chat attachments and other received files are not copied), plus, from the active vault, the dream journal folder and `Recuerdos.md` under `vault/` (spec 033 BR-23; the rest of the vault is not copied, and `dream-state.json` is not exported), and says which remote connection is chosen and whether the relay is on (never a credential). |
| Erasure | «Borrar mi historial» (conversations, received files including every chat attachment, voiceprint, the presence state of spec 034, the dream state of spec 033; a dream running then is aborted and saves nothing). Credentials: «Borrar» on each provider. |
| Retention / restriction | «Borrar conversaciones sin actividad» at 30/90/180/365 days (a deleted conversation takes its chat attachments with it, not the dream journals that cite it). Chat attachments also expire on their own 30 days after the conversation was last opened. |
| Rectification | Conversations and notes are text the person can edit. The memory lines the dream writes about the person are plain lines of `Recuerdos.md`, and each change it made is in the journal with the old line verbatim and its source, so the person can correct or undo it by hand. |
| Objection to processing by a provider | Change the agent's provider or delete its key; voice and embeddings can stay 100 % local. The dream is off by default and turned off with its switch; its provider follows the keys loaded. |
| Requests from third parties (if Alma processes other people's data, e.g. a customer's mail) | Handled by the responsible organization, with the same export and deletion mechanism, and the vault search to locate the data subject. |

## 4. Privacy by design

- Everything that can be local is local by default: Whisper, Kokoro, embeddings and the wake word run on the machine.
- Keys are sealed with the system store and do not reach the interface or the environment of commands.
- What leaves the machine is an explicit choice (provider per agent, channel by channel).
- The audit trail records *what* was done and *who allowed it*, never the content.
- The phone is a window, not a copy (spec 028): notes and conversations live in its memory while a screen is open and nothing is cached or stored (only its key, its push subscription and the app shell), every API response is `no-store`, and no push carries a title or text. Alma cannot stop the person from copying or screenshotting what the phone displays. While Tailscale is selected no new third party receives anything and the tailnet relays only encrypted traffic; with «Alma's relay» selected the relay and its host forward sealed traffic and see the metadata described in section 2.

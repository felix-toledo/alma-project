# Risk register

Alma's security and privacy risks, with their status. It is reviewed every quarter and every time an integration, a provider or a tool that acts outside the machine is added (ISO 27001 clause 6.1.2/8.2; SOC 2 CC3.2). **Likelihood (P) and impact (I)**: A high · M medium · B low. "Owner" is still to be assigned: the organization defines it.

| ID | Risk | P | I | Treatment | Status |
|---|---|---|---|---|---|
| R‑01 | **Dependencies with known vulnerabilities.** `pnpm audit` found 26 advisories (12 high), the most important **Electron 44.7.2 < 44.9.1** (Chromium patches), plus `nodemailer`, `body-parser`, `follow-redirects`, `fast-uri`, `uuid`, `minimatch` and nested ones from Excalidraw and pptxgenjs. | A | A | Electron is now 44.10.2 and `nodemailer` 10.4.0; the transitive ones are pinned to patched versions with `overrides` in `pnpm-workspace.yaml`; `pnpm audit` reports no known vulnerabilities. What unblocked it: `blockExoticSubdeps: false`, an exception accepted by the owner on 2026-11-08 for `libsignal` (a git dependency of baileys, R‑05), pinned by commit hash and integrity in `pnpm-lock.yaml`. Any other git dependency now needs a new decision. The overrides that cross a major (`image-size` 1→2, `uuid` 8→11, `katex` 0.16→0.18, `nanoid` 4→5) are covered by the tests and a smoke run of pptxgenjs, exceljs, mailparser and mermaid-to-excalidraw, not by a run through the real app screens. | 🟡 Mitigated, residual accepted |
| R‑02 | **Home Assistant listened on `0.0.0.0`** (`coordinator/home/engine.ts`, `managedConfig`). With WSL on *mirrored* networking it was exposed to the local network; the API gives control of the house and cameras. | M | A | `managedConfig` now writes `server_host: 127.0.0.1`; the app already reaches HA at `http://127.0.0.1:<port>` through WSL's localhost relay (checked on a real `alma-home` distro in NAT mode: a loopback-bound server answers from Windows). The file is rewritten at every start, so existing installs pick it up on the next engine start. Guarded by `tests/home.test.ts` › "R-02". Not covered: WSL mirrored networking was not tested; loopback inside the VM is shared with the host there, so it should hold. | 🟡 Mitigated, residual accepted |
| R‑03 | The user's sensitive environment variables (not Alma's) visible to `run_command`. | M | M | `commandEnv()` removes the keys of the providers Alma knows. The rest depends on the human approval of the command. | 🟡 Accepted |
| R‑04 | Conversations, vault and WhatsApp session in clear on disk if the machine is lost. | M | A | Require BitLocker/FileVault; technical option: encrypt `threads/` with a `safeStorage` key. | 🟡 Pending |
| R‑05 | **Baileys** (unofficial WhatsApp): it may violate WhatsApp's terms and get the number suspended; it brings a git dependency (`libsignal`) and is updated outside official channels. | M | M | Only the own chat, nothing mass-scale (already designed that way). Evaluate the official WhatsApp Business API if it is used with customers. | 🟡 Accepted |
| R‑06 | No signed packaging, no automatic updates and no Electron Fuses (`RunAsNode`, `EnableNodeCliInspectArguments` etc. stay at their defaults). | B today · A when distributing | A | When packaging: code signing, `@electron/fuses` with `RunAsNode` and `EnableNodeOptionsEnvironmentVariable` set to `false`, a signed update channel. | ⛔ Before distributing |
| R‑07 | Actions without approval by design: `home_*` tools (except locks/alarms), company agents with `COMPANY_AUTO_APPROVE`, «Siempre permitir» mode, and the Telegram `/home` panel (same device classes, same bound chat). An instruction injection could use them. | M | M | Switching to «Siempre permitir» asks for native confirmation; the audit trail records every execution and who allowed it; locks and alarms always ask for approval (in-chat confirmation on Telegram, audited as `home.control`). | 🟡 Accepted |
| R‑08 | The hash chain does not detect that the **end of the file is truncated** or that everything is deleted; it lives on the same machine. | B | M | Export the audit trail to separate storage (monthly) or send it to a SIEM; `verifyAudit()` already validates what is exported. | 🟡 Pending |
| R‑09 | DNS rebinding: a name changes address between the check and the connection of `fetch_url`. | B | M | Pin the resolved IP with an undici `dispatcher` (`ponytail:` note in `tools/web.ts`). | 🟡 Accepted |
| R‑10 | Two lockfiles (`pnpm-lock.yaml` current and `package-lock.json` obsolete): `npm install` would resolve versions different from the tested ones. | M | B | Delete `package-lock.json` and pin `packageManager` in `package.json`. | ⛔ Open (trivial) |
| R‑11 | "Instruction injection" in pages, mails or messages the agent reads, to make it use tools or leak data. | A | A | Layers: external results marked as data; human approval or auto-review of whatever is not a read; remote images blocked and CSP (no exit channel through the browser); `fetch_url` without local network; keys out of the commands' environment; audit trail. Residual risk: whatever the user approves without reading. | 🟡 Mitigated, residual accepted |
| R‑12 | Third-party MCP servers run code with the user's permissions. | M | A | Adding or changing them asks for a native confirmation that shows the command; per-server tool filter; minimal environment. | ✅ Mitigated |
| R‑13 | The data given to an agent travels to the chosen model provider. | A | M | The user chooses the provider per agent; inventory and legal basis in [PRIVACY.md](PRIVACY.md); no data if the agent uses a local model. | 🟡 Accepted with DPA (🏢) |
| R‑14 | **Remote access threats are explicit about their limits.** (a) The pairing fingerprint defeats pairing with the wrong host on the tailnet, not a compromised PC: whoever controls the PC confirms the pairing dialog. (b) A stolen session token is valid up to 1 hour. (c) An unlocked phone chats and answers approvals until revoked; only locks/alarms/gates need the passkey again. (d) Pairing depends on the browser carrying the URL fragment into the installed app (verified on iPadOS 27 and Chrome 156, re-checked on each major release); the typed-code fallback is not built. **Added by [028](../../.specify/specs/028-remote-vault-and-threads/spec.md) (2026-11-08):** (e) a stolen, unlocked, paired phone with History and its «continue conversations» sub-switch on can start a run inside any desktop conversation that is not a company's, with that conversation's own agent, model, working folder and tools, not only inside the shared remote thread. The approval policy is the app's normal one, not stricter for the phone: in «Permitir todo» mode `exec` and `write` run **without asking**, a phone-started run included; `publish` always asks and «Solo lectura» still blocks. A phone-started run spends the same provider tokens as one started on the PC. (f) Vault content now reaches the owner's phone over the tailnet (Notes scope, read-only, the active vault only); before, vault text left the PC only toward a model provider. The remote chat agent's own `read_note` and `search_knowledge` are unchanged and are not gated by the Notes scope. (g) Conversation titles (the first line of the first message) and message text are content: the list and the reads expose them to the phone; tool names, inputs, results, thinking and attachments are never sent, apart from what an approval card shows. (h) The PWA CSP now allows `img-src 'self' data:` because camera stills and note images arrive as base64; before, `img-src` fell back to `default-src 'self'` and neither rendered. It does not allow `https:`, `http:` or `blob:` images, and nothing else was loosened (`default-src 'self'`, `frame-ancestors 'none'`), so a note or a reply still cannot make the phone fetch from another host. (i) Cutting access aborts the runs the phone started and denies their pending approvals (tray kill switch, remote off, a revoked, forgotten or swept device; History or the sub-switch off aborts the by-id runs); text already committed stays. The shared-thread run is **not** aborted when only the chat scope is turned off (accepted decision). (j) A phone-started run in a Telegram, WhatsApp or voice conversation sends nothing to that channel: its approval prompt and streamed text are not forwarded or spoken, and an answer coming from that channel for a phone-owned approval is ignored (the PC window can still answer). (k) Alma cannot stop the phone from copying, sharing or screenshotting what it shows: accepted, not mitigated. (l) A folder renamed outside Alma leaves its exclusion (shown as stale; the new path is not excluded), and moving a note out of an excluded folder inside Alma widens access by the person's own act: accepted. | M | A | Everything off by default; step-up for sensitive actions; 1 h sessions, single-use 3-minute offers, 3-attempt lockout; revocation is immediate; audit of approvals, revokes and failures. For (e)–(l): Notes, History and the sub-switch are three separate switches, each off at every turn-on and each behind its own native confirmation; the exclusion list; one phone-started run per device; approvals only for the device that started the run, answered once, never «Siempre permitir»; the 15-day idle expiry, revoke and the kill switch; identical refusals; audit by path or id, never text. See [CONTROLS.md](CONTROLS.md). Residual: (a)–(d) and (e), (f), (g), (k), (l) above. ([026](../../.specify/specs/026-remote-access/spec.md), [028](../../.specify/specs/028-remote-vault-and-threads/spec.md)) | 🟡 Mitigated, residual accepted |

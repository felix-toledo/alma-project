## 1. Summary
Configuración → Imágenes becomes the one place where the person says which provider and model **create** pictures (what `generate_image` uses today) and which provider and model **see** pictures (what `look_at_image`, camera analysis, camera watches, plan-from-photo and the pictures attached in the chat use today, and which is set under Configuración → Casa). In both, the person may choose a provider and leave the model empty: Alma then asks that provider for its models and uses the newest one that can do the job (create or see). Casa stops being where the model that looks at pictures is chosen. A provider chosen only here, never acknowledged in the privacy notice, never silently receives pictures.

## 2. Problem and goal
Today the model that looks at pictures is configured under Casa ("Modelo que mira imágenes (planos y cámaras)", `settings.home.visionProvider` / `visionModel`), although it also reads the pictures a person attaches in the chat (spec 030); people do not look for it there. Also, a provider chosen there **without** a model is silently ignored: `pickVisionModel` (`src/shared/attach/readers.ts`) only honors the pair when both are set, otherwise it falls to the house agent, the default agent, any agent with a key. Creating pictures already accepts "provider only" (the newest image model of the service is looked up, 020 BR-5), but the look-up rule exists only for creation.

Goal: the person opens Configuración → Imágenes, sees one block for creating and one for seeing, picks a provider (and optionally a model) in each, and Alma uses what was picked; with a provider and no model Alma finds a suitable model for that job by itself, or says clearly that it could not. The privacy notice for attachments keeps naming the provider that really receives the picture, and a provider-only choice is used only after the person confirmed that provider by name.

## 3. Scope
**In:**
- The Imágenes tab: a "create" group (today's service + model) and a new "see" group (provider + model), each with the model field's suggestions and refresh button.
- The rule that resolves a provider with no model into a model, for seeing (new) and for creating (existing, restated).
- The per-provider table of which models can see (`shared`), one line per provider.
- Where the see setting is stored, how the existing `home.visionProvider` / `home.visionModel` values are carried over, and what Casa shows afterwards.
- The confirmation when a see provider is saved in Imágenes and the rule that a provider-only value is used only once acknowledged.
- What `look` (`src/coordinator/vision.ts`) and `threadReaders` / `pickVisionModel` (`src/shared/attach/readers.ts`) read afterwards.
- Failure behavior: no key, offline, provider with no model able to see or to create, listing error.
- Dictionary keys (Spanish and English) for the new texts; `docs/security/` and the module docs that name the vision model.

**Out (and why):**
- Giving the chat model native image blocks (pictures stay `look_at_image`, 020 BR-14, 030 BR-18): decided no (BR-8); a separate spec if the owner ever wants it.
- New providers, new image or vision clients (OpenAI has no chat client, so it cannot be a seeing provider; Anthropic, DeepSeek and Vercel have no image client in Alma, so they cannot create): not part of this spec.
- Per-agent or per-chat overrides of the create or see model: decided no (BR-15).
- Prices or cost estimates per model (BR-16).
- Video generation, image editing, upscaling (020 §3).
- Which model answers the house judgment rules and the agent's own chat: unchanged (`home.agentId`, 013/014).
- The composition tool `compose_image` (no model at all).

## 4. Users and stories
- **US-1** As the person, I want to choose in Configuración → Imágenes the provider and model that create pictures, so that I know where image generation is configured.
- **US-2** As the person, I want to choose in the same tab the provider and model that look at pictures, so that I do not hunt for it under Casa.
- **US-3** As the person, I want to pick only a provider and have Alma find a model of that provider that can create (or see), so that I do not track model names.
- **US-4** As the person, I want a clear message when my provider has no suitable model, or cannot be asked, so that I know what to change.
- **US-5** As the person, I want the privacy notice for attachments to keep naming the provider that really gets my picture, and no provider to receive my pictures or camera stills unless I confirmed it by name, so that choosing a provider here never sends a picture somewhere I was not told about.
- **US-6** As a person who already set a vision model under Casa, I want it carried over, so that I do not lose it or have my cameras start using something else.

### Resolving the model (US-2, US-3)
- **AC-2.1** (US-1) Given a create provider and a model, when `generate_image` runs, then that model is used with no listing call (020 AC-2.2, unchanged).
- **AC-2.2** (US-3) Given a create provider and no model, when `generate_image` runs, then the provider's models are listed and the newest image model is used, cached per service + URL + key for the life of the coordinator (020 AC-2.1, BR-5, unchanged).
- **AC-2.3** (US-2) Given a see provider and a model that the gate of BR-14 lets through, when any look runs (`look_at_image`, `camera_look`, camera watches, `home_plan_from_image`, a picture attached in the chat), then that model of that provider is used with no listing call and no capability check.
- **AC-2.4** (US-3) Given a see provider with a key that the gate of BR-14 lets through, no model, a provider with a rule in BR-13 and a listing that contains at least one model that rule accepts, when a look runs, then the model chosen by BR-5 is used for the look; the pick is cached for the life of the coordinator per provider + URL + key, and a later look reuses it with no listing call.
- **AC-2.5** (US-3, US-4) Given a see provider with a key and no model that the gate lets through, and either a provider without a rule in BR-13 or a listing that contains no model its rule accepts, when a look runs, then the look fails with a tool error that names the provider and says to pick a model in Configuración → Imágenes; for a provider without a rule no listing call is made; the picture is not sent to any other provider.
- **AC-2.6** (US-4) Given a see provider with a rule in BR-13 and no model, and the listing fails (offline, rejected key, timeout, HTTP error) or the provider has no key, when a look runs, then the look fails with a tool error carrying the provider's error (a missing key points to Configuración → Proveedores); nothing is cached from the failure and the picture is not sent elsewhere.
- **AC-2.7** (US-4) Given a create provider and no model, and the listing fails or contains no image model, when `generate_image` runs, then the fallback model of 020 AC-2.3 is used (unchanged behavior).
- **AC-2.8** (US-3) Given the model list, when a model is picked for seeing or for creating, then it is the last id in numeric-aware order (descending first, as for images, 020 AC-2.1), the same list always gives the same pick, and the pick is a pure function in `shared` (no clock, no network).
- **AC-2.9** (US-2) Given the see provider is empty (or is held back by the gate of BR-14), when a look runs, then the model is chosen as today: the house agent's, else the default agent's, else any agent whose provider has a key, else the first agent (020 AC-5.5), with no capability check.
- **AC-2.10** (US-3) Given the capability table of BR-13, then it has one entry for each of the five chat providers (a missing entry fails typecheck), an id is accepted only when its provider's entry accepts it, and a provider whose entry is "none" accepts nothing (unknown = cannot see). Flipping DeepSeek or Vercel to "can see" is a change of that one entry.

## 6. Business rules
- **BR-1** Two independent settings: **create** (provider, model; `settings.images`, rules 020 BR-4 and BR-5) and **see** (provider, model; stored as `settings.images.vision { provider, model }`, both strings, empty = not set). A provider may be chosen with the model empty in both. The old `settings.home.visionProvider` / `visionModel` stop being stored: a one-time migration (a flag in the settings, as `metaDefaultApplied` does for Meta) copies them over and empties them.
- **BR-2** A model set in either group is used as is, with no listing call and no capability check (the person is in charge; 020 AC-2.2), subject only to the gate of BR-14 for seeing.
- **BR-3** A provider set with no model is resolved by listing that provider's models (`Provider.listModels`, `listImageModels`, which return model ids only: Alma has no capability metadata today) and classifying the ids (BR-4). Resolution runs in the coordinator at the moment of use; it needs the key and the network.
- **BR-4** *What can create / what can see* is decided from the model ids by one pure, tested function per job in `shared`. For creation, the existing patterns stay (xAI `image|imagine` but not `video|edit`; OpenAI `gpt-image*`/`dall-e*`; Meta `muse-image*`, 020 AC-2.1), moved from `coordinator/images.ts`. For seeing, the table of BR-13.
- **BR-5** Among the ids a rule accepts, the model chosen is the newest: the last in numeric-aware id order, descending first (as for images, 020 AC-2.1). Across families this is an order of ids, not of release dates (for Anthropic it lands on the family whose name sorts last); the person can type another model (BR-2).
- **BR-6** The providers a group offers are the ones for which Alma has a client for that job: create = Meta, xAI, OpenAI (`ImageProviderId`); see = Anthropic, xAI, DeepSeek, Vercel AI Gateway, Meta (`ProviderId`, a chat client that takes images, 005 AC-3.7). OpenAI has only a key slot for images (005 BR-1). Each dropdown marks "falta la key". Changing the provider clears the model.
- **BR-7** When the see provider is empty the model is chosen by the existing fallback chain (house agent, default agent, any agent with a key, first agent) with no capability check, and the tab shows which model that resolves to. If that agent's model cannot see, the look fails with the provider's own error (020 AC-5.8).
- **BR-8** A look does not change: effort `low`, no tools, fixed English system prompt, 8 MB and the three roots (020 BR-13, BR-15), and pictures never enter an agent's conversation (020 BR-14, 030 BR-18). The chat model does not follow this setting: no native image blocks.
- **BR-9** The notice names the provider from settings alone: a provider is a setting, a model is a lookup (AC-4.1). A failed lookup never changes the provider (AC-4.4).
- **BR-10** The classification and the pick (BR-4, BR-5, BR-13), the migration from `home.vision*`, the gate of BR-14 and the "who reads this picture" decision are pure functions in `shared` with the model list and the acknowledged list injected; `coordinator` does the listing and the cache; `renderer` only shows and asks. The pure `pickVisionModel` stays synchronous and network-free because `main` calls it for the native dialog and cannot import `coordinator` (Constitution III, IV); for a provider with no model it returns the provider and an empty model, and the coordinator completes it.
- **BR-11** No new tool and no change to any `ToolRisk`: `look_at_image` stays `read` and standalone, `generate_image` stays `write` (020 BR-1).
- **BR-12** Failures and cache. For seeing: a missing key, an offline app, a listing error or no accepted model is a tool error; the failure is not cached, the picture goes nowhere else, and a successful pick stays cached for the life of the process per provider + URL + key (nothing is persisted; a new model appearing mid-session is picked up on restart or by typing it). For creating: the existing fallback ids (020 AC-2.3).
- **BR-13** *Capability table* (`shared`, one entry per `ProviderId`, a rule or "none"; unknown = cannot see, never guess). Decided on the owner's delegation and open to veto: Anthropic: ids `claude-*`. xAI: ids `grok-*` that pass `isChatModel`. Meta: ids `muse-spark*`. **DeepSeek: none. Vercel AI Gateway: none.** The Providers tab labels both "solo texto"/"text only" and their ids mix labs or are unconfirmed, so they have no automatic pick until the owner says which ids see; a model typed by hand still works (BR-2). The rows of xAI and Meta follow the provider capabilities written in `docs/modules/providers.md` ("text and images") and are as narrow as the id patterns of the model picker allow; a model that can see whose id does not match is simply not auto-picked.
- **BR-14** *Acknowledgement gate* (pure, `shared`, the one function that both the looks and the notice use). A see provider is used when its model is typed (an explicit pair, as today and as carried over from Casa), or when its model is empty and the provider is in `attachments.noticeAcknowledged`; otherwise the fallback chain of BR-7 is used. Why: a provider-only value used to be ignored, so honoring it unconditionally would start sending camera stills (background watches have no notice) to a provider the person only clicked in a dropdown or inherited from a half-set Casa value; the typed pair is a complete, explicit choice that already worked this way. Saving a see provider in Imágenes asks the confirmation of AC-4.8 and records it in the same list the chat and phone notices use, so anything chosen through the new tab is acknowledged by construction; the gate only holds back what came without that confirmation (a carried-over provider-only value).
- **BR-15** The create and see settings are global: no per-agent or per-chat override (the chat's own model per conversation, 024, is unrelated).
- **BR-16** Cost: the existing sentence about camera watches (`home.think.visionNote`) is shown under the see group and in Casa's read-only line; no prices or estimates (Alma has prices only for companies, 005 BR-16).

## 7. Constraints and risks
- **Layers touched** (see `docs/architecture.md`):
  - `shared`: the `Settings` type and defaults for the see setting (`types.ts`, `defaults.ts`), the sanitizing/migration on load, the capability table, the classification, pick and gate functions, `attach/readers.ts` (`pickVisionModel`, `threadReaders`), dictionary keys (`i18n/es|en`); `home.ts` loses the two vision fields.
  - `main`: `settings.ts` load path (carry-over, key-in-model wipe for the new field, shape of `images` after the shallow merge on load and in `update`); `main` calls `threadReaders` for the native dialog, no new IPC beyond the existing ones expected.
  - `coordinator`: `vision.ts` (`visionModel` becomes async where a listing is needed), `images.ts` (shares the listing and cache), `index.ts` (`images.models` gains a mode for the see group, or a sibling request), `attachments/service.ts` (`attachments.readers` stays sync).
  - `renderer`: `SettingsDialog.tsx` `ImagesTab` (second group and the confirmation), `home/HomeSettings.tsx` (the selector goes). UI built only from what the Imágenes tab and the chat notice already use (`card`, `field`, `row`, native `select`, `input` + `datalist`, `ghost small` refresh button with `Icon`, `primary small` save, the existing confirmation pattern of the chat notice or `confirm()`) in Umbra tokens; no new component, color or spacing. Keyboard and gamepad reachable (native controls or `data-focusable`), touch targets at least 44 px, focus as in `umbra-ui`. The plan names the exact components.
- **Security / privacy:** no new tool and no new category of stored personal data (the acknowledged list already exists). The data flow does not change in kind (a picture goes to the vision provider), but **which provider** can now change through a setting outside Casa that can be a provider only; the gate (BR-14) and the confirmation (AC-4.8) keep that from sending anything to a provider the person did not confirm by name, and the notice keeps naming the real receiver (AC-4.1 to AC-4.4). A carried-over provider-only value keeps today's behavior until confirmed. Residual case, unchanged from today: a complete pair carried over from Casa and never acknowledged keeps receiving camera stills as it did. Listing models sends the provider's key to the provider as today (005). `docs/security/PRIVACY.md` (the vision provider row and the notice paragraph) and `CONTROLS.md` change in the same PR; the omission recorded in CONTROLS (`look_at_image` not in the PRIVACY provider table) can be closed in the same edit.
- **Performance / platform:** one model-list request per provider and process on the first look (cached; BR-12), not on every look; camera watches look every 10 s or more (014), so the lookup must not run per look. The gate reads settings at each look (cheap, no I/O). Offline: a model set explicitly works without the list; a provider-only setting needs the list at least once. No new dependency.
- **Known trap:** `settings:update` replaces top-level keys whole and the loader merges `images` one level deep, so an `images` patch that omits the see part would erase it (AC-1.8).

## How to work (applies to every task)
- Read first: `.specify/memory/constitution.md`, `docs/architecture.md`, `.specify/specs/027-alma-e2e-relay/spec.md` and `plan.md`, `.specify/specs/026-remote-access/spec.md` (the channel you must not change), `docs/context.md` ("remote access" terms).
- **Test first, seen failing for the right reason.** Create the exported signature with a wrong or empty body, write the test, run `pnpm exec vitest run tests/<file>`, see an assertion fail (not "module not found"), then write the code. Name each test with its AC id: `it('AC-3.2 …')`; titles in the spec's `Planned:` lines are the ones to use.
- Each task ends with `pnpm run check:fast` green. Never `--no-verify`, never `biome-ignore` without a written reason, never lower a threshold. pnpm only. **Add no dependency** (PD-8): if a task seems to need one, stop and report.
- Style: no `;`, single quotes, English identifiers, user-facing text only through dictionary keys (`src/shared/i18n/{es,en}`; the phone's through its own dictionary), comments only for the why. Commits `type(area): summary`, no Claude co-author line.
- **A deliberate change to the security layer must update `tests/support/remote-protected.json`** (the checked-in SHA-256 manifest of the protected files, checked by `tests/remote-relay-contract.test.ts`), in the same commit and in plain sight.
- **Do not edit the security layer.** `src/coordinator/channels/remote/{channel,authorize,session,limits,pairing-flow,devices-admin,store,tailscale,tailscale-transport,monitor,chat,approvals,home,cameras,notes,threads,runs,thread-view,quiet,push,audit,activity}.ts` and `src/shared/remote/{api,authorize,pairing,limits,wire,status,webauthn,view,push,tailscale}.ts` stay byte-identical. The one allowed edit in `transport.ts` is `'relay'` in the `id` union. T17 fails the build if you break this; if a task seems to need such an edit, stop and report.
- Layers (`docs/architecture.md`, `tests/support/arch.ts`): `shared` imports nothing; `coordinator` never imports `main`/`renderer`, never `electron` outside `index.ts`; the phone client imports only itself and `src/shared/remote/`; `src/relay/` imports only itself and `src/shared/remote/{relay-frame,relay-limits,crypto}`.
- Secrets never in logs, audit entries, errors, fixtures or prompts (BR-7). Tests generate fake keys on the spot.
- Files that many tasks touch (`src/shared/types.ts`, `src/shared/i18n/{es,en}.ts`, `src/coordinator/index.ts`, `src/main/index.ts`, `src/main/messages.ts`, `src/renderer/src/remote/RemoteSettings.tsx`, `src/remote-client/usePwa.ts`, the PWA dictionaries): **two tasks that touch the same one never run in parallel.**
- A task whose diff is only glue says so; commit it with `[no-tests: <reason>]` as `scripts/require-tests.mts` allows, and the logic it wires is tested in the earlier task it names.
- UI tasks (T30, and the PWA screens in T26 and T27) load the `console-ui` and `umbra-ui` skills first and use only their tokens and components; invent none.
- Numbers in tests come from `REMOTE_RELAY_LIMITS` and the exported constants, never literals (they are tunable defaults, BR-28).

## Known nits
Found in the review of T1 to T32 and not done, to pick up when touching the file:
- `src/relay/route.ts` repeats the routing-id pattern of `relay-config.ts` (`isRoutingId`) because the relay zone may not import it; keep the two in step.
- `RoomObject` keeps one `WeakMap` of socket wrappers and one `id` field set by `roomFor`; a room serving two ids would be a bug, but nothing asserts it.
- A request without `cf-connecting-ip` is counted under the key `unknown`, one shared bucket; right for a platform that always sets it, harsh if it ever does not.
- `logCounters` runs on every socket close of a room, so a reconnecting PC logs a line each time; aggregate across rooms only if the volume matters.
- `answerGate` casts the shared limits' verdict to `boolean`; `createAddressLimits` is synchronous, a future asynchronous one would need the cast removed.

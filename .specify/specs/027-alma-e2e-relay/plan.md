## 1. Approach
The relay is a third `RemoteTransport`. Everything that is new sits on one side of the transport interface: on the PC a `RelayTransport` (outbound WebSocket, end-to-end host, request mapping), on the phone an end-to-end client behind the existing `pwaFetch` seam, between them a relay server that forwards sealed frames and keeps nothing. The pure parts (frame schemas, key schedule, handshake, counters, shell gate, limits) are in `src/shared/remote/relay-*.ts`, browser-safe, and are shared by the PC, the phone and the relay. The security layer (`channel.ts`, `authorize.ts`, `api.ts` and the flows) is not edited; a source scan with a negative fixture proves it (AC-2.3), and the 026 suites run again over the relay pair prove it behaves the same (AC-2.1). The relay server is Cloudflare Workers plus one Durable Object per routing id (PD-6), in this repository as the sixth architecture zone `src/relay/` (BR-18); its platform-independent logic (`RelayRoom`) is tested in Vitest against an in-memory fake, and only a thin adapter touches the platform.

Alternatives rejected: a Node server on a VPS (needs a `ws` dependency, patching and an always-on machine for a service that must keep nothing); serving the relay as a Tailscale-like overlay (out by inheritance); WebSocket on the phone (026 PD-6 and BR-27); mixing the pairing secret into the key derivation (cannot be done without changing the channel, §1.2). ADR [0022](../../../docs/adr/0022-alma-e2e-relay.md) records the shape.

| PD-1 | **Where each piece lives.** Shared pure core: `src/shared/remote/relay-frame.ts` (the wire contract), `relay-crypto.ts` (WebCrypto wrappers), `relay-e2e.ts` (key schedule, counter window, handshake machine, sealed session), `relay-shell.ts` (`acceptShell`), `relay-limits.ts` (`REMOTE_RELAY_LIMITS`). | PD-2 | **Wire protocol.** Phone to relay, HTTPS, host `<routing id>.<relay domain>`: `GET /relay/v1/info` answers `{relay:true, v:1}` (the PWA's switch into relay mode; the Tailscale transport answers 404 so the same bundle serves both); `POST /relay/v1/frame` carries one JSON `Frame` and returns one. Every other GET is the static shell. PC to relay, `wss://<id>.<domain>/relay/v1/pc`, JSON text messages: relay sends `{k:'challenge', nonce}`; PC answers `{k:'reg', pub, sig}`; relay answers `{k:'ready'}` or closes with a code (4001 refused, 4002 replaced, 4003 id held by another key, 4008 over a cap, 4009 version); then relay to PC `{k:'f', rid, frame}` and `{k:'abort', rid}`, PC to relay `{k:'r', rid, frame}`; keepalive is a WebSocket ping answered by the platform's auto-response so an idle PC does not wake the Durable Object. Relay-level refusals are plain JSON with an HTTP status and no secret: `{error:'offline'}` 503 (PC not connected), `{error:'full'}` 429, `{error:'timeout'}` 504 after 35 s, `{error:'version'}` 426, `{error:'gone'}` 410 (session unknown to the PC). The PWA never calls `/api/...` on the relay origin; the real path, headers and body are inside the sealed frame. | BR-27: PC outbound WebSocket, phone plain HTTPS through the seam. One request is one frame in and one frame out, so the relay needs no per-session state of its own. |
| PD-3 | **Handshake and key schedule (BR-24, BR-25), over two HTTPS round trips.** `hs1` phone to PC in clear: protocol version, ephemeral P-256 public key `ea`, nonce `na`. `hs2` PC to phone in clear: session id `sid` (16 random bytes), ephemeral `eb`, nonce `nb`, the PC identity public key, and an ES256 signature by the PC identity key over `H("alma-hs2" ‖ v ‖ ea ‖ na ‖ eb ‖ nb ‖ sid)`. The phone verifies the signature with the PC key it stored at pairing, or, while pairing (nothing stored), with the key in `hs2` only if its fingerprint equals the one read from the QR; otherwise it aborts before sending anything (`remote.pwa.relay.mismatch`). Both derive `z = ECDH(ea, eb)`, `th = SHA-256(hs1 ‖ hs2 fields)`, `prk = HKDF-Extract(salt = th, ikm = z)`, then four keys by HKDF-Expand with labels `hs-c2s`, `hs-s2c`, `c2s`, `s2c`. `hs3` phone to PC sealed under `hs-c2s` (counter 0): either `{deviceId, sig}` where `sig` is the device key's ES256 signature over `H("alma-hs3" ‖ th)`, or `{anonymous:true}` (pairing). `hs4` PC to phone sealed under `hs-s2c`: `{ok:true, expiresAt}`. The device id and its signature therefore never cross the relay in clear. The PC accepts `hs3` only if the device is known, not revoked and not idle-expired and the signature verifies; every other case is the same generic refusal. An anonymous session may send any request; the unchanged channel refuses everything but the pairing routes (AC-2.5). | Mutual authentication with forward secrecy (both ephemeral), identity hiding for the device, no change to what the channel computes. The mixing of the QR secret that the human asked for is replaced by the fingerprint check (§1.2). |
| PD-4 | **Sealed frames, counters, replay, request to response.** A request frame is `{v, t:'q', sid, ctr, ct}`; `ct = AES-256-GCM(k_c2s, nonce(ctr), plaintext, aad = v ‖ 'q' ‖ sid ‖ ctr)`; `nonce = 4 zero bytes ‖ 8-byte big-endian ctr`. The answer is `{v, t:'a', sid, ctr (the request's), ct}` sealed under `k_s2c` with the same nonce rule and `aad = v ‖ 'a' ‖ sid ‖ ctr`; one key per direction, one answer per request, so no nonce is ever reused under a key. The phone numbers its requests with a strictly increasing counter and accepts exactly one answer per pending counter. The PC accepts request counters through an anti-replay window of 64 (a bitmap below the highest seen), so parallel requests (two held polls plus short ones) that the network reorders still pass while a replay or a counter older than the window is rejected. Any authentication failure, replay or malformed frame drops the frame and ends that session (BR-25); the PC answers the next frame for it with the plain `{error:'gone'}` and the phone handshakes again. | A window is the standard answer to unordered parallel requests; tying the answer to the request counter removes a second counter and makes a swapped answer fail authentication. |
| PD-5 | **Rekey and lifetime.** A session lives 1 hour from `hs4`; the PC refuses frames after that with `gone`; the phone re-handshakes at 55 minutes. When the PC's relay connection is re-established, the PC clears every session (so a reconnect always means new keys, AC-3.11). Session keys are never persisted. Browser support: WebCrypto ECDH P-256, HKDF, AES-GCM and ECDSA are in every browser the 026 PWA already needs (ES256 and non-exportable device keys are used today), but this is not verified on the phones Alma targets: spike V1 and the manual walk H3. | AC-3.11, BR-24. |
| PD-6 | **Hosting platform: Cloudflare Workers plus Durable Objects.** One Worker routes by `Host` to the Durable Object `RelayRoom` named by the routing id; Workers Static Assets serve the shell from the same Worker; a wildcard route `*.<relay domain>/*`. The PC's socket is accepted with the WebSocket Hibernation API and its small per-connection state (hash of the registered key) is stored as the socket's attachment, so it lives and dies with the connection and nothing touches Durable Object storage. Facts supplied by the coordinator, all to be re-verified in spike V2 before deploy: the hibernation API exists; an inbound WebSocket message may be up to 32 MiB (our 4 MiB cap sits well below); incoming WebSocket messages are billed at 20 to 1 as requests; the free plan requires SQLite-backed Durable Objects (declared with `new_sqlite_classes`; we declare it and never use the storage API, enforced by a source scan, AC-6.1). Alternatives rejected: a Node VPS (PD above); a platform without a per-id stateful object (the rendezvous needs one place where the PC's socket and the phone's request meet). The relay domain must be a registrable domain whose per-PC names are first-level subdomains, so the free wildcard certificate of the zone covers `<id>.<domain>`; a name two levels deep needs a paid certificate (spike V2). | OQ-1 to OQ-13. The platform is lock-in the human accepted by choosing the maintainer-operated model; ADR 0022 records it. |
| PD-7 | **Caps, billing and the emergency stop.** `REMOTE_RELAY_LIMITS` holds the BR-28 defaults (frame 4 MiB, 1 PC connection, 15 phone connections, 900 frames a minute, 1 GiB a day, 120 attempts a minute per address, 10 unknown-id attempts a minute then 5 minutes, 10 anonymous handshakes a minute per id). Cost per phone request is about one Worker request plus one Durable Object request plus one twentieth of a request for the PC's answer; the free plan's daily request allowance is the effective global cap and the maintainer's budget ceiling (placeholder) is the point at which the caps are tightened. | OQ-12, BR-22, BR-28, BR-29. |

Also PD-2/PD-10 (T14): the keepalive is the text `ping` from the PC answered `pong` by the platform (the runtime's WebSocket client cannot send protocol pings); the PC pings every 25 s and closes a socket that has said nothing for 70 s. ### 1.2 Corrections to the spec found while planning (for the human to confirm on return; each is cheap to change)
1. **AC-4.2 and BR-25: no secret mixing, no digits over the transcript.** The 6 digits are `pairingCode(secret, phoneKey, pcNonce)` and `pcNonce` is generated inside the channel's pairing machine (`shared/remote/pairing.ts`, `pairing-flow.ts`). The transport cannot reach the offer secret, and changing the inputs is a channel change. The protection the human asked for (a relay in the middle at pairing is caught) is delivered by PD-3: the PC signs the transcript and the phone checks it against the QR fingerprint, which never passes through the relay. A device-key substitution is still caught by the unchanged digits. If the human wants the literal behavior, the cost is an additive hook in `PairingFlow` (a context blob inside the code's HMAC) and an amendment of the constraint that the channel stays unchanged.
2. **BR-26, AC-3.12, the notice key: the "pin" is a gate, not a wall.** A service worker cannot veto the replacement of itself by the origin, so the PC-signed gate does not stop a deliberate swap. The spec, §7, the notice text and ADR 0022 now say so. The stricter alternative is OQ-3 option (c).
3. **AC-2.8: there is no bypass of the seam.** The earlier draft said `lib/request.ts` calls the global `fetch` directly; it takes `fetch` as a parameter and every call site already passes `pwaFetch`. The criterion now scans that only `http.ts` touches the global `fetch`.
4. **Runtime outages cannot use the channel's `reportOutage`.** It is Tailscale-specific. PD-11 overlays the relay state at the composition root instead.

## 3. Contracts

## 4. Data and persistence
- PC: `<dataDir>/remote/relay-sealed` (JSON sealed through the existing `SealBox`): `{ routingId, pairedDomain }`. Created on first selection of the relay, deleted by erase. Nothing in `settings.json` except `remote.transport`. Device records are the 026 ones, untouched; a device paired through the relay is an ordinary record.
- Phone: the device key and PC key per origin (IndexedDB, as now), the shell cache; nothing new beyond the PC's public key and the running shell hash.
- Relay: nothing persisted (BR-15). The Durable Object class is declared SQLite-backed because the free plan requires it and its storage is never used. Per-connection state rides on the hibernating WebSocket's attachment and ends with the connection.
- Existing installs: `sanitizeRemote` maps any unknown `transport` to `tailscale`; no migration.

## 5. Dependency injection
- `RelayTransport` receives identity signing, the device-key lookup, the WebSocket constructor, clock, randomness, a state callback and an audit callback. Tests pass a fake WebSocket wired to `tests/support/relay-fake.ts` (an in-memory relay built on the real `RelayRoom`) and a key pair generated on the spot.

## 7. Security and privacy impact
- **ToolRisk:** none (BR-6). Test AC-1.6 pins it.
- **Secrets:** session keys memory only; the routing id and nothing else sealed on the PC; the PC identity key already sealed by 026. Logs, audit and errors never carry them (AC-3.6, AC-6.2).
- **Third parties:** the maintainer as operator and Cloudflare as hosting provider, named in `PRIVACY.md`; Cloudflare's own logs are outside the relay's code and are minimized and disclosed (V9).
- **New surface and residuals (all go to R-14):** the outbound WebSocket; a per-PC address open to the internet (pairing flood can lock pairing for 5 minutes, accepted); the routing id visible in DNS and TLS to a network observer (accepted, provisional OQ-18); a known residual denial of service after a relay restart (first valid claimant of an id wins until the real PC re-registers; mitigation path: the id commits to the PC's public key); the active-operator limit of the shell (PD-13); traffic analysis by size and timing.
- **Docs: what belongs to the planning stage and what to the code.**
  - Done with the plan (this PR): ADR 0022 (`docs/adr/0022-alma-e2e-relay.md`), its index row and the pointer lines in ADR 0020 and 0021, the fix of ADR 0020's stale "proposed / nothing is in the code yet" body, the README rows, the glossary terms, and a "planned, not built" note in R-14 of `docs/security/RISKS.md` so the residuals are on the register before the code lands.
  - With the code (task T32, same PR as the implementation, because `CONTROLS.md` and `PRIVACY.md` describe what exists and Constitution V ties them to the change): the full R-14 rows, `CONTROLS.md` (relay row, end-to-end row, the amended "only the owner" row), `PRIVACY.md` (provider rows, retention, the traffic-analysis limit, the Tailscale sentence), `docs/modules/remote-access.md` (and its "no cloud relay" limit), `docs/architecture.md` (sixth zone), the amendments of §7.1 of the spec (026, 028, 006, 022, 001) and the exit rule text.

## 8. Rollout
- **Setting and default:** `remote.transport` defaults to `tailscale`; the relay needs its own native confirmation; remote access itself is still off by default and every scope off at every turn-on. Until spec 001 delivers signing and Fuses the default does not change (AC-1.12).
- **Turn off:** selecting Tailscale, the tab switch, the tray item, Alma quitting; each closes the WebSocket and ends every session at once (AC-1.7).
- **First run:** the wizard gains a "How the phone connects" step; choosing the relay shows `remote.relay.sees`, `remote.relay.notice.shell` and `remote.relay.notice.operator` before the relay dialog.
- **Deploying the relay (the human, last tasks):** supply the three facts, create the Cloudflare account, the domain and an API token, run the publish check, `pnpm dlx wrangler@<pinned> deploy`, set `RELAY_PAUSED` to test the stop, set the wildcard route and certificate, record the shell root hash in the release notes. No PC build ships a working relay before this; `RELAY_DOMAIN` is the string `RELAY_DOMAIN_PLACEHOLDER` until the human sets it, and a packaged app whose domain is still the placeholder does not offer the relay, so nobody can select a relay that does not exist (AC-6.7).
- **Exit rule:** BR-29, written into ADR 0022 and `docs/modules/remote-access.md`.

## 1. Summary
If the person turns it on, Alma "dreams" once a night. While the person sleeps (between 02:00 and 06:00, or as soon as the PC is back if it was asleep or off then), Alma rereads the conversations it has not dreamt yet with the cheapest model the person has a key for, in a fixed pipeline with no tools, and without asking adds, replaces and removes lines of its memories of the person in `Alma/Recuerdos.md`. It writes a journal note for that night in the vault, `Alma/Sueños/YYYY-MM-DD.md` (`Alma/Dreams/` in English), saying what it changed, why, and which conversation each change came from, plus a speculative section of hunches that it shows but does not treat as fact and that never enters a prompt unasked. Spending is capped per night. The dream also writes a short morning greeting; at the first sign the person is up (their first message of the day, or, with spec 034, unlocking, waking or starting the PC after a long absence), Alma delivers it once, on Telegram, as a desktop notification and, with the History scope on, as a content-free notification on the paired phone; opening Alma then lands in that greeting conversation. With the dream off, nothing of this happens.

## 2. Problem and goal
Alma's memory only grows: the person or an agent adds lines, and nothing ever reviews, merges or corrects them, so an outdated fact stays in every prompt and Alma asks again what it was already told. Alma also never speaks first in a useful way at the start of the day, because it does not know when the day starts for the person.

Facts the design respects (verified in code and docs; `alma_codebase.md` cites lines):
- A **Memory** is a bullet line of `Alma/Recuerdos.md` (`Alma/Memories.md` in English, `shared/types.ts`), injected into every system prompt. `remember` appends (3-300 characters), `forget` removes by exact or unique-substring match, and the 4000-character total (`MAX_MEMORY_CHARS`) is enforced only by `remember`. Lines carry no date, origin or importance. `KnowledgeBase` has no bulk rewrite.
- `remember`, `forget` and `save_knowledge` have risk `memory`: never asked, blocked only in the read-only approval mode (`docs/modules/approvals.md`).
- Threads are one JSON file each under `<userData>/threads/`. A message has `role`, `content`, `ts` and no id, so a message is identified by its thread id plus its `ts`.
- The vault is indexed (FTS5 + bge-m3) and **Recall** injects the closest fragments of any vault note into every run. A journal written in the vault is therefore recallable unless excluded.
- `Alma/Recuerdos.md` is outside «Exportar mis datos» and «Borrar mi historial»; PRIVACY says the vault belongs to the person and is deleted from the vault.
- `privacy.threadRetentionDays` (default 0 = keep) deletes threads with no activity; a journal citing a thread can outlive it.
- `RoutineRunner` ticks every 30 s and only while Alma runs; a daily routine missed overnight is caught up only the same calendar day (018 BR-4). Wake timers are unreliable under Modern Standby (report).
- Cost is estimated only for companies, with `costOf` and one list price per provider (`PRICES`, `shared/company.ts`, a `ponytail:` note says per-model prices are not modeled). Providers in `PRICES`: `anthropic`, `xai`, `deepseek`, `vercel` (a gateway whose price is a guess), `meta`.
- Desktop notices go through the `notify` message (suppressed when the window is focused unless `always`, which also shows the in-app alert). Telegram's `notify` sends to the bound chat and returns false when not connected; the bound chat feeds a single thread (`telegram.threadId`).
- The phone push (026 BR-27, AC-11.1, 028 AC-4.3) is content-free, has one fixed text, and is sent only for a pending approval while the approve scope is on.
- Pending approvals never time out (004 AC-8.6) and, for routine runs, never reach Telegram (`docs/modules/telegram.md`).

Done means: with the dream on, each night that has something new produces one dream, its changes to `Recuerdos.md` and one journal that cites the source of every change, within the cost cap; the person gets exactly one greeting on the first wake signal of the day, on the channels they have, and lands in it when they open Alma; with the dream off, no conversation is reread and no provider is called for it; and every failure (no key, no vault, read-only mode, offline, provider error, interrupted) ends in a defined state the person can see in the status line.

## 3. Scope
**In:**
- An opt-in switch (off by default), the cost-cap setting, the provider and model the dream would use now, and a status line under the switch (last dream's date, estimated cost, last failure reason).
- When to dream: the fixed night window, catch-up after a missed night, one retry after a failure, at most one dream a night, a pure "is a dream due" function.
- What the dream reads, and the marking of everything not typed by the person and not written by Alma as untrusted data.
- The dream as a fixed pipeline with no tools: coordinator code reads, the model returns structured output validated with Zod, coordinator code writes.
- Choosing the model from a fixed economy-model table; estimating and capping the cost.
- The journal note and its sources; its exclusion from automatic recall; the writes to `Recuerdos.md` (additions, replacements, removals) and how they meet concurrent edits and the 4000-character total.
- «Exportar mis datos» copying the journal folder and `Recuerdos.md`.
- The morning greeting: written by the dream, what triggers it, once a day, its conversation, its delivery to Telegram, the desktop and the phone (one more fixed push text, amending 026 BR-27), landing in its conversation, and expiry.
- Failure paths: no key, no vault, offline, provider error, invalid model output, cap reached, interrupted, switch turned off, read-only mode.
- Docs and security entries (§7.1), in the same PR as the implementation.

**Out (and why):**
- A review step or a diff the person accepts before memories change: the owner decided the dream writes without review.
- A per-night cap on the number of changes: the owner decided none.
- Cascade deletion of what the dream derived (journal lines, embeddings) when a thread or memory is deleted: the owner decided none.
- Protected memories (lines the dream may not touch): the owner decided none until lines carry metadata (Q4).
- Unattended approvals, their timeout and quiet hours: moved to spec 035 (owner Q1, 2026-11-09), because the timeout and the Telegram routing change every unattended run (routines, house rules, companies) and this spec needs neither, since the dream never asks (BR-15). Recorded here so nothing is lost, with each item's status as given: (owner, 2026-11-08) unattended approvals go to Telegram; (proposed 2026-11-08, not objected to, to be confirmed in 035) a pending unattended approval times out after 24 hours, is then rejected and the person is notified; quiet hours 23:00-08:00 honoring Windows Focus; 3 pushes a day per channel from the initiative engine, the morning greeting excluded. Spec 035 amends 004 AC-8.6 ("no timeout"). The only part this spec keeps is BR-31 (the greeting is exempt from quiet hours once they exist).
- Initiatives, interruption budgets, feedback buttons: spec 035.
- An agent run with tools for the dream: the owner chose a fixed pipeline (Q2).
- Home Assistant presence as a wake signal: Alma does not model it yet.
- Voice (spoken greeting) and the WhatsApp self chat as greeting channels: not among the channels the owner chose.
- Waking the PC to dream (wake timers, `powerSaveBlocker`): unreliable on Modern Standby; catch-up replaces it.
- A configurable night window: fixed in v1 (Q27).
- Metadata on memory lines (dates, importance, decay scores), compressing old threads into episode summaries, knowledge notes written by the dream: not asked for; the dream writes only the journal and `Recuerdos.md` (Q6).
- A picker for the dream's model, and a confirmation when the provider changes: the owner chose "cheapest", named next to the switch (Q11).
- Retrying a failed greeting delivery, and a notification for a failed dream: the owner decided none (Q25, Q27).

## 4. Users and stories
- **US-1** As a person, I want to turn the dream on knowingly (what it reads, which provider and model get it, what it may write without asking me, what it costs) and off at any time, so that nothing rereads my conversations unless I chose it.
- **US-2** As a person, I want Alma to consolidate what it learned while I sleep, adding, correcting and removing its memories of me, so that it stops asking what I already told it and stops relying on facts that changed.
- **US-3** As a person, I want a dated journal of each night saying what changed, why and which conversation it came from, including the speculative hunches, so that I can see, correct or undo what it decided.
- **US-4** As a person whose PC sleeps or is off at night, I want a missed dream to happen when the PC is back, so that I do not lose the night.
- **US-5** As a person, I want one greeting at the moment I am up, on Telegram, the desktop and my phone, and opening Alma to take me to it, so that what it prepared reaches me without my looking for it.
- **US-6** As a person, I want the dream's spending capped per night, so that a busy day cannot run up a bill.
- **US-7** As the owner, I want text written by other people (WhatsApp, mail, web pages, tool results) to reach the dream only as data and never as instructions, so that nobody can plant a memory by sending me a message.
- **US-8** As the maintainer, I want the decisions (when to dream, which model, what to read, when to greet) in pure tested functions in `shared`, the dream as a fixed pipeline with no tools, and the new risks documented, so that the rules are testable without a model and Constitution V holds.

## 6. Business rules
(owner) marks the owner's decisions of 2026-11-08 (BR-7 of 2026-11-09). (owner, confirmed 2026-11-09) marks defaults proposed on 2026-11-08 and confirmed by the owner on 2026-11-09. (owner Qn) marks the owner's answer of 2026-11-09 to Open Question Qn (the planner's recommendation, accepted). Unmarked rules apply an existing written rule.

- **BR-1** (owner) The dream is opt-in: off by default, and only the person turns it on.
- **BR-2** (owner; owner Q11, Q14) The dream uses the cheapest model among the providers that have an API key loaded: a fixed table in `shared`, next to `PRICES`, holds one economy model per provider; providers are ranked by that model's input price (a dream reads far more than it writes); the gateway (`vercel`) is excluded while its price is a guess; ties are broken by the table's fixed provider order. There is no model picker. The provider and model it would use now are named next to the switch and in the journal; turning the dream on or a change of provider asks for no further confirmation.
- **BR-3** (owner; owner Q4) The dream writes without review: the journal (BR-33) with sources (thread id plus message `ts`), and new memories, replacements and removals of memories in `Alma/Recuerdos.md`. Every replaced or removed line is kept verbatim in the journal so the person can restore it by hand. No memory is protected from the dream. There is no per-night cap on the number of changes.
- **BR-4** (owner) Deleting a thread or a memory does not delete what the dream derived from it (journal lines, embeddings, other memories).
- **BR-5** (owner; owner Q13) The speculative section is shown to the person in the journal. It is never written to `Recuerdos.md` (it is not a fact by definition). The whole journal folder is excluded from automatic recall and stays reachable with `search_knowledge` and `read_note` when an agent asks, so a hunch never enters a prompt unasked.
- **BR-6** (owner; owner Q22, Q23) The morning greeting goes to Telegram, a desktop notification and a notification on the paired phone (the phone one only with the History scope on, BR-30). Opening Alma lands in the greeting conversation as BR-29 says.
- **BR-7** (owner, 2026-11-09) `send_telegram` stays `memory`, with no limit, whoever calls it. This spec adds no limit to it.
- **BR-8** (owner, confirmed 2026-11-09; owner Q9) Content not typed by the person and not written by Alma (tool results, web pages, mails, other people's WhatsApp messages) is read only because the person turned the dream on, and always as untrusted data, never as instructions. The person's own messages in any channel are trusted.
- **BR-9** (owner, confirmed 2026-11-09; owner Q15) Cost cap: USD 0.25 a night by default, configurable between USD 0.01 and 5, estimated from token usage at list prices as company budgets are. It is checked before each model call; when the next call would cross it, the dream stops, applies what is complete, says in the journal that it stopped at the cap and how many conversations it did not read, and those roll to the next dream. The cap covers everything spent that night, a retry included. A dream stopped at the cap has a greeting only as BR-27 says.
- **BR-10** (owner, confirmed 2026-11-09) Journals are kept forever: Alma never deletes them.
- **BR-11** (owner, confirmed 2026-11-09; owner Q27) Night window 02:00-06:00, local time, fixed in v1 (not a setting). A night with no dream in the window is caught up when Alma starts or the PC resumes. No OS wake timer is used.
- **BR-12** (owner, confirmed 2026-11-09) Wake signals: the person's first message of the day in any channel, or the wake signal of spec 034 (unlock, resume, return after idle, or Alma starting however it was started, after an absence of 4 hours or more; 034 BR-2, BR-3, BR-12). Home Assistant presence is out.
- **BR-13** At most one dream per night and one greeting per day; both states are persisted so a restart does not repeat them (otherwise "once" would not hold). The day starts at 02:00 local, the start of the night window (034 BR-4, owner 034 Q1).
- **BR-14** (Constitution IV) The decisions are pure exported functions in `shared` with tests: whether a dream is due, which model, what to read and how to frame it, whether the greeting is due. The coordinator is a thin shell around them; dependencies (threads, knowledge base, providers, channels, clock) are injected.

## 7. Constraints and risks
- **Layers touched:** `shared` (settings types and defaults, the economy-model table, the pure decisions of BR-14, the Zod schema of the dream's output); `coordinator` (a dream runner next to `routines.ts`, reading `ThreadStore`, writing through `KnowledgeBase`, providers, recall's exclusion of the journal folder, export, the greeting conversation and its delivery through `notify`, Telegram and the remote push; 034's presence message); `main` (settings persistence; 034's presence events; landing the window on the greeting conversation); `renderer` (the settings switch, provider name and status line, landing in the conversation); `remote-client` (the greeting notification and landing, with the History scope).
- **Security / privacy:**
  - New flow of personal data: conversations already sent once to their own provider are sent again, in bulk, to the dream's provider, which may be a provider the person never chats with (the cheapest one with a key, named next to the switch). `docs/security/PRIVACY.md` gains this flow.
  - New stored personal data: the journal (derived facts and hunches about the person, with references to conversations), kept forever and surviving the deletion of its sources (owner, BR-4), exported with «Exportar mis datos» and untouched by «Borrar mi historial» (BR-23).
  - New risk, accepted by the owner's rule (BR-3) but required by Constitution V to be documented in `docs/security/RISKS.md`: **false memories** (the model invents or misreads a fact, it enters `Recuerdos.md` and then every prompt, with no review) and **memory poisoning by injection** (a WhatsApp message, a mail or a web page read in a thread carries an instruction that the dream turns into a memory nobody reviews, or uses to remove a true one). Mitigations: untrusted framing (BR-8), the journal with verbatim old and removed lines and sources (undo by hand), a fixed pipeline with no tools and nothing outward (BR-15), the read-only mode stops it (BR-15), the journal excluded from automatic recall (BR-5). Residual: a model can still be fooled.
  - Tool risk: no new tool (BR-15). The dream's writes are governed as `memory`.
  - Outward channels: the greeting adds one fixed, content-free push text (amending 026 BR-27) and a Telegram message to the bound chat; no new third party beyond the dream's provider choice.
  - No new secret.
- **Performance / platform:** a busy day can mean many threads; the cap (BR-9) and the reading rule (BR-21) bound it. Local time and clock as routines (018). Modern Standby: catch-up, not wake timers. A dream reads files that runs may be writing (AC-2.6, BR-20). A large `Recuerdos.md` written by hand may already exceed 4000 characters (BR-18).
